# postman-flow

Native HTTP workflows use `.http.yml` document specifications. Plain-text YAML files and future
GUI canvases compile to the same format-independent `FlowDefinition`. Compilation produces an
immutable `FlowPlan`, which is then executed by supplying an HTTP transport and session inputs.

```rust
pub fn parse_flow_yaml(source: &str) -> Result<FlowDocument, DocumentError>;
pub fn write_flow_yaml(document: &FlowDocument) -> Result<String, DocumentError>;

pub fn compile_flow(
    source: &FlowDefinition,
    api_catalog: &ApiCatalog,
    environment: &CompileEnvironment,
) -> Result<FlowPlan, Vec<Diagnostic>>;

pub fn execute_flow<T: HttpTransport>(
    plan: FlowPlan,
    transport: T,
    session: FlowSessionEnvironment,
) -> Result<impl Stream<Item = Result<FlowEvent, FlowError>> + Send, FlowError>;
```

## Running Workflows

The product entry point is `postman-g` (crate: `postman-cli`). Both `.http` and `.http.yml`
compile into the same `FlowPlan`:

```bash
# Static check: parses and compiles without creating a transport or sending requests
cargo run --locked -p postman-cli -- run \
  crates/postman-flow/examples/flows/httpbingo_catalog.http.yml --check

# Execute: compiles, connects to HTTP endpoints, and streams events and outputs
cargo run --locked -p postman-cli -- run \
  crates/postman-flow/examples/flows/httpbingo_catalog.http.yml \
  --input client=hello
```

`--input` and `--var` are interchangeable aliases. Objects, arrays, booleans, `null`, quoted
JSON strings, and integers without leading zeros preserve their JSON types; numeric-like strings
such as `00123` remain strings. Undeclared inputs are ignored. `--check` only compiles without
sending network requests.

The `run_yaml` example can also drive the crate API directly, matching `postman-g run` behavior.

Seven example documents are available in `examples/flows/`:

- `httpbingo_minimal.http.yml`: Two-step UUID extraction and reuse.
- `httpbingo_order_chain.http.yml`: Three-step order scenario simulation.
- `httpbingo_multi_hop.http.yml`: Five-step pipeline with multi-hop references.
- `httpbingo_dynamic_chain.http.yml`: Eight-step flow with IDs generated by independent `/uuid` responses.
- `httpbingo_json_values.http.yml`: Chaining JSON values across requests, preserving escaping and data types.
- `httpbingo_catalog.http.yml`: Reusable API catalog, named outputs, and visual canvas coordinates.
- `httpbingo_loops.http.yml`: Bounded collection iteration, aggregation, and idempotent polling.

HTTPBingo scenarios provide request echoing and UUID generation to verify orchestration behavior
without invoking external state changes or billing effects.

## YAML v1 Specification

```yaml
schema_version: 1
flow:
  name: uuid
  inputs:
    - name: host
      default: https://httpbingo.org
  steps:
    - id: seed
      request:
        kind: http
        method: GET
        url:
          concat:
            - input: host
            - literal: /uuid
      checks:
        - kind: status
          equals: 200
      exports:
        - name: id
          path: $.uuid
  outputs:
    - name: id
      value:
        output: { step: seed, name: id }
editor:
  nodes:
    seed: { x: 100, y: 150 }
```

The top-level structure consists of `schema_version`, `flow`, optional `apis`, and optional
`editor`. `flow` contains `name`, `inputs`, `steps`, and `outputs`. Step `name` is optional
and defaults to `id`. Steps execute in declaration order; output references must point to exports
declared by earlier steps. Headers are defined as a list of `{name, value}` pairs, preserving
order and duplicate keys.

Inputs without a `default` are required; `default: null` sets the default to JSON null. Session
inputs override defaults at runtime, including explicit nulls. `sensitive: true` can be set on
inputs and exports; returned flow outputs inherit sensitivity, and debug formatting redacts their
values. Re-serializing a document preserves declared defaults; runtime inputs are never persisted
into the file.

`editor.nodes` maps step IDs to `{x, y}` canvas coordinates and is ignored by the compiler.
Drafts can be saved with incomplete steps or unresolved references, but must compile before
execution. Document files store definitions, catalogs, and layout, not compiled plans, run outputs,
selection state, or undo history.

## References and JSON Expressions

Text templates use explicit branches without recursive interpolation:

```yaml
literal: ordinary text
```

```yaml
input: host
```

```yaml
output: { step: seed, name: id }
```

```yaml
concat:
  - literal: 'Bearer '
  - output: { step: login, name: token }
```

String literals do not evaluate `{{...}}` or other embedded template syntax. `concat` combines
explicit text parts without URL-encoding; encoded values must be supplied directly.

### Dynamic variables and calculations

Built-ins do not need input declarations. Use `{input: $timestamp_ms}` for Unix milliseconds,
`{input: $timestamp}` for Unix seconds, `{input: $uuid}` / `{input: $guid}` for UUID v4, and
`{input: $randomInt}` for an integer from 0 through 999. Each reference is evaluated when used;
export a returned value if it must be reused across steps. Explicitly declared inputs override
the corresponding built-ins, which also permits deterministic tests. In `.http` files the same
variables use interpolation, for example `{{$timestamp_ms}}` or `{{$uuid}}`; an explicit
`@$timestamp_ms = 1234` declaration can provide an overridable default.

Text and JSON expressions both accept `calc`:

```yaml
calc: 'floor((step-1.balance * 0.9 * 3) / step-2.price)'
```

Calculations support `+`, `-`, `*`, `/`, unary signs, parentheses, scientific notation, and the
single-argument functions `floor`, `ceil`, `round`, and `abs`. Inputs and previous-step exports
must contain numbers or numeric strings. Bare input names use letters, digits, `_`, and `$`;
hyphenated step names retain the `step-1.balance` syntax. Subtraction such as `balance-1` and
`step-1.balance-1` works without spaces. Wrap unusual references in backticks, e.g.
`` `risk-factor`-1 ``. When a subtraction could also be a hyphenated step reference, use spaces
(`balance - step.price`) or quote each reference. Declared input names take precedence over
step-output notation with the same name.

Syntax, function names and references are checked before execution. Expressions are limited to
64 nested levels, 4096 tokens and 64 KiB. Division by zero, non-finite inputs and arithmetic
overflow fail the step before its request is sent. Arithmetic uses IEEE-754 `f64`, not exact
decimal arithmetic; decimal rounding at a boundary requires care.

### HMAC-SHA256 signing

```yaml
request:
  kind: http
  method: GET
  url:
    concat:
      - literal: 'https://example.com/account?timestamp='
      - input: $timestamp_ms
  auth:
    type: hmac_sha256
    secret: {input: api_secret}
    param: signature  # optional; defaults to signature
```

This is Binance-style parameter signing: HMAC-SHA256 over the serialized URL query followed
directly by the optional `url_encoded` body, with no extra separator. The digest is lowercase
hex. Query order, duplicate parameters, `+` and existing percent escapes are preserved; URL
fragments are excluded. With no body, the signature is appended to the query; with a form body,
it is appended to the body and a form Content-Type is supplied unless one is already set.
All templates, including the secret, are resolved before signing. The secret is not sent.

The signature parameter must be a nonempty URL-unreserved name and must not already exist in
the query or form. Other body kinds are rejected for this signing mode. This is not a general
OAuth2, AWS or arbitrary-body signing implementation. Mark secret inputs `sensitive: true` as
with other credentials.

Structured JSON bodies:

```yaml
body:
  kind: json
  value:
    object:
      order_id: { output: { step: order, name: id } }
      quantity: { input: quantity }
      enabled: { literal: true }
      optional: { literal: null }
      label:
        string:
          concat:
            - literal: 'Order: '
            - output: { step: order, name: id }
      items:
        array:
          - literal: 1
          - literal: "00123"
      ordinary_data:
        literal: { input: this-is-data-not-a-reference }
```

JSON expressions support `literal`, `input`, `output`, `object`, `array`, and `string`.
Input and output references preserve their underlying JSON types; `string` explicitly encodes
concatenated text as a JSON string scalar. Ordinary object data can be wrapped in `literal` to avoid
keyword collisions. Object keys are never evaluated as templates.

Other body modes:

```yaml
body:
  kind: json_template  # also supports raw, url_encoded
  value:
    literal: '{"client":"already escaped"}'
```

`json_template` preserves raw template interpolation without automatic JSON quoting or escaping.
Invalid literal JSON is rejected at compile time; runtime rendering errors fail the step before
sending the HTTP request. `body` can be omitted or set to `kind: none`.

## Conditional Execution (`when` and `coalesce`)

Steps can declare an execution guard using `when`. If the condition evaluates to `false`,
the step is skipped without sending an HTTP request, its checks and exports are bypassed,
and a `StepSkipped` event is emitted.

```yaml
- id: branch-paid
  name: Paid branch (status == 2)
  when:
    eq:
      - output: { step: query-status, name: status }
      - literal: 2
  request: ...
```

Supported condition operators:
- `eq`, `ne`: `[left, right]` (equality / inequality)
- `gt`, `gte`, `lt`, `lte`: `[left, right]` (numeric and lexicographic ordering)
- `in`: `[item, collection]` (array element membership or substring check)
- `and`: list of sub-conditions (all must evaluate to true)
- `or`: list of sub-conditions (at least one must evaluate to true)
- `not`: negates an inner condition

Numeric strings in ordering comparisons are parsed as exact decimals, including scientific
notation. Quote large amounts and high-precision decimals (for example,
`{ literal: "100000000000000000001" }`) so YAML/JSON floating-point parsing does not round them
before the condition runs. A string compared with a JSON number uses the number's serialized
decimal representation. Equality between two strings remains textual; ordering between
non-numeric strings remains lexicographic.

`and` and `or` short-circuit. A missing output is an evaluation error unless a short-circuited
branch avoids it or `coalesce` supplies a fallback. Invalid type comparisons report type names
without including operand values.

### Result Convergence with `coalesce`

When downstream steps or flow `outputs` need to consume a value produced across mutually exclusive
conditional branches, use `coalesce` to select the first available candidate:

```yaml
invoice:
  coalesce:
    - output: { step: branch-paid, name: invoice }
    - output: { step: branch-unpaid, name: invoice }
    - literal: "INV-DEFAULT"
```

## Bounded Iteration and Polling

`for_each` resolves a JSON array once, binds each item and optional zero-based index inside its
body, and can collect selected child exports for later steps:

```yaml
- id: process-orders
  kind: for_each
  items: { output: { step: list-orders, name: orders } }
  as: current_order
  index_as: order_index
  max_iterations: 100
  on_error: fail_fast # or continue
  steps:
    - id: fetch-order
      request:
        kind: http
        method: GET
        url:
          concat:
            - { input: host }
            - { literal: /orders/ }
            - { input: current_order }
      exports:
        - { name: detail, path: $.data }
  exports:
    - name: details
      collect: { step: fetch-order, name: detail }
```

When a collected source step is skipped by `when`, that collection omits the value and the
iteration can still succeed. No `null` placeholder is inserted. Each collection preserves the
order of its executed sources, so collections from different conditional branches may have
different lengths. If all sources for a collection are skipped, its result is an empty array.
Actual request, check, or export failures still follow the loop's error policy.

With `on_error: continue`, later items still run and failed iterations contribute no collected
value. An unhandled transport cancellation stops the loop and propagates through enclosing loops
even with `continue`; no later iterations or steps run. `fail_fast` stops at the first failed
iteration. Item/index bindings are loop-local, and sensitivity on collected child exports
propagates to the resulting array.

`repeat_until` executes its body immediately and evaluates `fail_when` after each successful
iteration. If it matches, the loop ends with `FailureCondition` without evaluating `until` or
updating `carry`. Otherwise it evaluates `until`, then waits before the next attempt if needed.
The first body execution counts toward
`max_iterations`; exhausting the iteration or time limit fails the flow.

```yaml
- id: wait-for-receipt
  kind: repeat_until
  max_iterations: 20
  interval_ms: 3000
  timeout_ms: 60000
  until:
    eq:
      - { output: { step: query-receipt, name: status } }
      - { literal: success }
  fail_when:
    eq:
      - { output: { step: query-receipt, name: status } }
      - { literal: failed }
  steps:
    - id: query-receipt
      request:
        kind: http
        method: GET
        url: { input: receipt_url }
      exports:
        - { name: status, path: $.status }
```

Cross-iteration state must be explicit. `carry` initializes a loop-local binding before the first
iteration and updates it from a child export only when another iteration will run. This supports
cursor pagination without making stale child outputs implicitly visible:

```yaml
carry:
  - name: cursor
    initial: { literal: start }
    from: { step: fetch-page, name: next_cursor }
```

Loops may nest three levels. `max_iterations` is limited to 10,000, polling intervals to 1–60,000
ms, and polling timeouts to 1–86,400,000 ms. Dropping the execution stream cancels an active wait or
request and prevents later iterations. Use polling only for idempotent reads such as receipt/status
queries; the runtime never implicitly retries approval, signing, or transaction broadcast.

## Assertions and Outputs

```yaml
checks:
  - kind: status
    equals: 200
  - kind: jsonpath
    path: $.json.quantity
    equals: { input: quantity }
```

The `equals` field in `jsonpath` is a typed JSON expression; string `"123"` does not match integer
`123`. `jsonpath_template` accepts text expressions and preserves text-to-JSON coercion semantics.
New documents should prefer `jsonpath`.

JSONPath selectors support root `$`, dot-separated object keys, and array indices (e.g.
`$.items[0].id`), excluding wildcards and filters. Step `exports` extract values from responses,
and flow `outputs` declare which inputs or step exports are returned to the caller.

Every declared check executes; any check failure or export extraction failure halts the flow.
Step exports commit only after all checks and extractions for that step succeed. The terminal
event is `FlowFinished { success, outputs }`, with empty outputs on failure. Transport errors are
standard failed run outcomes rather than stream-level errors.

## API Catalog

Reusable operations can be declared under `apis` in the document or supplied directly to
`compile_flow` as an independent catalog. See `httpbingo_catalog.http.yml` for an example.

Catalog `parameters` define local names referenced via `input` within the definition. Calling steps
use `request: { kind: api, api: ID, bindings: ... }`, where bindings evaluate in the caller's scope.
Compilation snapshots and validates both scopes. Bindings resolve lazily in the caller's scope,
while all expressions in the API request, including `calc` and `auth.secret`, resolve against
the API parameters and built-ins. Direct input/output bindings preserve their JSON types;
text bindings render as strings. The request cannot implicitly capture unrelated flow inputs.
Missing or extra arguments, unknown API IDs, and cross-step references inside definitions produce
compile diagnostics.

Compiled plans own request and binding snapshots; modifying the source definition, catalog, or layout
leaves existing plans unchanged. A single plan can be cloned and executed across multiple sessions
with isolated variable state.

## Diagnostics, Persistence, and Limits

- `DocumentError`: YAML syntax errors include line and column numbers; version and shape errors include field paths.
- `Vec<Diagnostic>`: All compilation errors discovered across normalized definitions, step IDs, and API IDs.
- `FlowError::InvalidInputs`: Missing required inputs or undeclared inputs supplied at runtime.
- Stream `InvariantViolation`: Internal invariant violation of a compiled plan.

Step shapes are checked before normalization: HTTP steps require `request`, `for_each` requires
`items`, `as`, and `steps`, and `repeat_until` requires `until` and `steps`. Missing or null required
fields and fields belonging to another step kind produce schema errors with their field paths.
HTTP exports require `path`; collection exports require `collect`. Structurally complete drafts
(such as empty loop bodies or unresolved references) can still round-trip and are rejected by the
compiler until completed.

Unknown fields, unsupported versions, duplicate mapping keys, custom YAML tags, non-string mapping keys,
and non-finite numbers are rejected. YAML merge keys (`<<`) are not expanded and remain ordinary keys in
literal JSON objects. Document size is limited to 2 MiB and 96 nesting levels; JSON expressions are
limited to 64 levels. Step count can be constrained via `CompileEnvironment::max_steps`.

`write_flow_yaml` emits canonical formatting and verifies roundtrip loadability. It preserves
definition and layout semantics without preserving original comments, whitespace, key ordering, or
number representations.

Version 1 implements sequential HTTP execution, conditional branches, bounded collection loops,
and bounded condition polling. Parallelism, implicit retries, API type schemas, and GUI canvas
interaction remain separate future additions.

`execute_flow` returns a statically dispatched `impl Stream`. Creating the stream does not send
requests; dropping it stops subsequent steps without rolling back already completed HTTP operations.

cargo test --locked -p postman-flow --all-targets
cargo clippy --locked -p postman-flow --all-targets -- -D warnings
